# Feature Specification: 视频墙（拼接屏）模式下发

**Feature Branch**: `main`（未新建分支；本规范与 2026-09-19 缺陷修复同批交付）

**Created**: 2026-09-19

**Status**: Implemented / 由 2026-09-19 缺陷修复反向补齐规范，`plan.md` 与 `tasks.md` 待 `clarify` 后生成

**Input**: 用户要求「修新运行时切换大屏模式时，拼接屏不动作的 bug」，并把视频墙下发补成正式规范：切换大屏模式时向 50 个拼接屏输出节点下发控制包（清屏 → 映射 → 提交 → 刷新），失败时不得假报成功；覆盖下发协议、阶段时序、失败语义与 Simulation/Hardware 分工。

## 背景与规范缺口 *(可追溯性)*

- `specs/001`、`002`、`003` 只描述「单/双大屏模式」这一运行态字段及其窗口静音策略，全文没有出现「视频墙 / 拼接屏」。003 迁移时 `scp_cv/services/video_wall.py` 只有**控制包构造**被迁到 `VideoWallSequenceBuilder`，下发层（协议阶段、并发上限、重试退避、失败中止）既没有任务承接，也没有任何规范条目要求它存在。
- 结果：.NET 运行时的 `PATCH /api/runtime/` 与预案激活只写数据库，物理墙面完全不动作（Bug 1，2026-09-19 修复）。
- 本规范把该能力固化为可审查条目。后续再动运行态模式、预案激活、SafetyMode 装配或设备网络时，MUST 逐条对照本文件，避免同类静默漏迁。

## Clarifications

### Session 2026-09-19

- Q: 本规范是否覆盖「拼接屏电源开关」？ → A: 不覆盖。拼接屏电源（`192.168.5.10:8889`）是设备服务的静态 TCP 指令，由 003 的设备合同与 `DeviceService` 负责；本规范只管画面映射下发。
- Q: `single/double` 与物理布局的对应关系可否由实现重新定义？ → A: 不可以。`single → 工作站 2-1 铺满整墙`、`double → 左半墙工作站 2-1 + 右半墙工作站 2-2` 是现场接线与组播地址已固化的外部约束，不是实现选择。
- Q: 协议细节（节点清单、包字节、端口、组播地址）算需求还是技术方案？ → A: 算需求。它们是与第三方硬件的对外约定，改协议就是改需求；字节级布局可另在 `plan.md`/`research.md` 展开。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 切换大屏模式时墙面画面真正改变 (Priority: P1)

操作员在仪表盘或播放控制页点击「单屏 / 双屏」，或在预案里配置了大屏模式并激活预案。物理拼接屏随即改画：切到单屏时整面墙显示工作站 2-1 的画面，切到双屏时左半墙显示工作站 2-1、右半墙显示工作站 2-2。

**Why this priority**: 这是本功能存在的唯一理由。界面上模式变了而墙面没变，现场就会按错误的画面继续讲解；旧 Python 版具备该行为，迁移后丢失。

**Independent Test**: 以 `-SafetyMode Hardware` 启动控制主机，用一个监听 4830 端口的假节点集合（或等效抓包）替代真实墙面，触发模式切换并核对收到的包序、目标集合与裁切参数；物理画面对照另见 SC-007。

**Acceptance Scenarios**:

1. **Given** 运行态为 `double`、墙面正常，**When** 通过 `PATCH /api/runtime/` 切到 `single`，**Then** 全部 50 个节点依次收到清屏、映射（组播 `224.1.1.55`、工作站 2-1 裁切为整墙 10×5 分块）、提交、刷新四类包，接口成功返回，运行态为 `single`。
2. **Given** 运行态为 `single`，**When** 切到 `double`，**Then** 左半墙（列 0–4）映射到 `224.1.1.55` 的工作站 2-1、右半墙（列 5–9）映射到 `224.1.1.56` 的工作站 2-2，裁切按半墙 5×5 分块，运行态为 `double`。
3. **Given** 预案中 `big_screen_mode_state=set`，**When** 激活该预案，**Then** 先按预案模式下发视频墙，成功后运行态、静音策略、窗口目标按预案生效。
4. **Given** 运行态已是 `single`，**When** 再次请求 `single`，**Then** 仍然完整下发一遍（用于墙面掉电或失步后的现场补救），不得因为「模式没变」而跳过。

### User Story 2 - 下发失败时界面不假报成功 (Priority: P1)

节点不可达、网络抖动或墙面设备离线时，切换必须整体失败：运行态停在原模式，静音策略不变，预案激活整体中止，接口返回明确错误，操作员看到的是「没切成」，而不是「界面已切、墙上还是旧画面」。

**Why this priority**: 运行安全优先要求不得假报成功。静默半成功会让操作员按错误画面继续，比直接报错危险得多。

**Independent Test**: 让一个节点在整段重试内始终不可达，触发切换，比较接口错误码、运行态字段与静音窗口集合；再让失败发生在映射阶段，核对提交/刷新阶段是否一个包都没发。

**Acceptance Scenarios**:

1. **Given** 某个节点在 5 次尝试后仍失败，**When** 该失败发生在清屏阶段，**Then** 映射、提交、刷新三个阶段一个包都不发，接口返回 400 且错误体 `code=video_wall_error`，运行态与静音策略与切换前逐字段一致。
2. **Given** 清屏阶段全部成功、映射阶段有节点失败，**When** 切换，**Then** 提交与刷新不发，运行态不变，错误信息至少包含失败节点的 `IP:端口`、阶段名与原因，最多列 5 条并以「其余 N 个失败」收尾。
3. **Given** 预案含大屏模式、系统音量与窗口目标，**When** 视频墙下发失败，**Then** 整个激活中止：运行态、音量、静音策略、窗口目标全部保持激活前状态，接口返回 `code=scenario_error`。
4. **Given** 墙面部分节点已执行清屏但后续阶段失败，**When** 操作员看到错误，**Then** 文档与提示明确「墙面可能停在已清屏状态」，不承诺硬件回滚（数据库事务不覆盖硬件副作用）。

---

### User Story 3 - 现场排障与常规运行等待可控 (Priority: P2)

切换是同步操作：正常情况下秒级返回；异常情况下必须在有限时间内给出成败结论，不能无限等待。日志要能定位到是哪几个节点、哪个阶段、重试了几次。

**Why this priority**: 控制台写操作共用同一数据库写通道，长时间阻塞会连带卡住媒体源与预案编辑。

**Independent Test**: 用可控延时的假节点测单次切换耗时与日志内容；核对网络等待是否发生在数据库写事务之外。

**Acceptance Scenarios**:

1. **Given** 墙面与网络正常，**When** 切换模式，**Then** 95% 的请求在 3 秒内返回。
2. **Given** 节点「能连上但不响应」的最坏情况，**When** 切换，**Then** 单次请求在 90 秒内返回明确失败，不出现无限等待或静默超时；期间其它控制台写操作（如编辑媒体源）不被数据库写锁阻塞。
3. **Given** 某节点在第 3 次尝试成功，**When** 切换，**Then** 日志记录该节点、阶段、尝试序号与退避等待，便于判断链路质量。

---

### User Story 4 - 开发与模拟环境不误连现场硬件 (Priority: P2)

在没有墙面的开发机上以 Simulation 模式运行时，模式切换必须完全不产生网络包，但仍拒绝非法模式；只有现场以 `-SafetyMode Hardware` 启动时才走真实 TCP。

**Why this priority**: 与显示器拓扑、系统音频的既有分工一致；开发机误发控制包会改动现场画面。

**Independent Test**: Simulation 下触发切换，断言没有任何外发连接且运行态正确更新；Hardware 装配在集成测试中可解析出真实实现。

**Acceptance Scenarios**:

1. **Given** `-SafetyMode Simulation`，**When** 切换单/双屏，**Then** 不向任何节点发送 TCP 包，运行态与静音策略照常更新。
2. **Given** 任意模式，**When** 请求一个非法模式（如 `triple`、空串），**Then** 立即拒绝且不下发任何包。
3. **Given** `-SafetyMode Hardware`，**When** 控制主机启动，**Then** 视频墙控制器、TCP 传输与下发参数都能被正确解析出来（装配错误不得只在现场暴露）。

---

### Edge Cases

- 墙面设备或交换机刚上电：部分节点慢响应——靠重试退避覆盖，耗尽后整体失败。
- 两个操作员近乎同时切换模式：两次下发不得交错，后一次在拒绝前一次之后整段执行。
- 控制主机重启：不自动重下发（保持旧版语义），墙面维持上次映射；操作员可重复请求同一模式补救。
- 墙面本身掉电或失步而运行态未变：重复请求同一模式必须完整重下（见 US1-4）。
- 节点 IP 互换补丁（现场 screen_id 45/46 对调）：目标集合按补丁后的 IP 计算，不得漏发或重发同一台。
- 单屏下仍可对窗口 2 发指令：窗口 2 的画面不可见但会话仍在，模式回切后按预案/会话恢复。
- 请求被取消（客户端断开、停机）：取消必须显式传播，不得把取消包装成下发失败或反过来假装成功。
- 墙面处于「已清屏未提交」的中间态时再次切换：允许直接重下完整序列，不需要额外的复位协议。

## Requirements *(mandatory)*

### 物理与协议约束 *(外部约定，不是实现选择)*

- 墙面为 10 列 × 5 行共 **50** 台输出节点，地址 `192.168.5.101~150`，控制端口 **TCP 4830**；节点坐标 `col×5+row` 计算 screen_id 时，**45 与 46 必须对调**（现场接线补丁）。
- 每台节点每次切换收到 **4 个包**：清屏（`61 FF`）、窗口映射（`61 02`，45 字节、含校验和）、提交（`61 B8`）、刷新（`61 B9`）。
- 映射包携带源组播地址与裁切区：工作站 2-1 用 `224.1.1.55`（窗口 1），工作站 2-2 用 `224.1.1.56`（窗口 2）；单屏时源 `3840×2160` 按 `384×432` 分成 50 块铺满整墙，双屏时按 `768×432` 分成左右各 25 块。
- 节点只接受写入、不回读状态；画面正确性最终只能由现场画面确认，不能由接口返回值推断。

### Functional Requirements

- **FR-001**: `PATCH /api/runtime/` 与含 `big_screen_mode_state=set` 的预案激活 MUST 在改变运行态之前真正下发视频墙控制包；仅写数据库不算完成。
- **FR-002**: MUST 保持 `single → 工作站 2-1 铺满整墙`、`double → 左半墙 2-1 + 右半墙 2-2` 的映射语义，不得重新定义布局或组播地址。
- **FR-003**: MUST 按 清屏 → 映射 → 提交 → 刷新的顺序整段下发；映射阶段开始前 MUST 保留清屏到映射的固定间隔（200 ms），避免节点把新映射叠加在旧画面上。
- **FR-004**: 同一阶段内的发送 MUST 并发执行，并发上限为 25；不同阶段之间 MUST 串行，不得重叠。
- **FR-005**: 单个节点的单次发送 MUST 有明确超时（2 秒）并开启 TCP_NODELAY；超时不得无限等待。
- **FR-006**: 单节点发送失败 MUST 重试，最多 5 次，退避间隔 0.2 / 0.4 / 0.8 / 1.0 秒；重试成功 MUST 留下日志。
- **FR-007**: 任一阶段出现最终失败节点时 MUST 立即中止后续阶段，不得提交半套映射；错误摘要 MUST 包含 `IP:端口`、阶段与原因，最多列 5 条并以「其余 N 个失败」收尾。
- **FR-008**: 下发失败时 MUST 整体不生效：运行态模式与固定静音策略保持原值，接口返回 400 且 `code=video_wall_error`。
- **FR-009**: 预案激活中下发失败 MUST 中止整个激活（音量、运行态、静音策略、窗口目标都不执行），返回 `code=scenario_error`。
- **FR-010**: 模式的固定静音策略（`double` 静音窗口 3/4；`single` 再静音窗口 2）MUST 只在下发成功后应用，与运行态更新同一次提交。
- **FR-011**: 非法或未知模式 MUST 在下发前被拒绝，且不产生任何网络包。
- **FR-012**: 重复请求当前已生效的模式 MUST 仍完整下发一遍（现场补救路径），不得短路。
- **FR-013**: 同一进程内并发下发 MUST 串行化，任何时刻只有一次完整序列在执行。
- **FR-014**: 网络等待（含重试与超时）MUST 发生在数据库写事务之外，单个控制台请求的最坏阻塞 MUST 有界（≤ 90 秒）并在超界前给出明确失败。
- **FR-015**: `-SafetyMode Simulation` MUST 不产生任何外发网络包，但 MUST 保持模式校验与运行态更新；只有 `-SafetyMode Hardware` 走真实 TCP。
- **FR-016**: `-SafetyMode Hardware` 下的视频墙实现、TCP 传输与下发参数 MUST 能独立解析（装配可测），不得依赖仅在应用启动路径才会被触发的隐式默认值。
- **FR-017**: 取消令牌 MUST 显式传播：调用方取消时不得被当作节点失败上报，也不得对外声称成功。
- **FR-018**: 每次成功下发 MUST 记录模式与包数；失败 MUST 记录阶段、失败节点数与原因。日志 MUST NOT 包含凭据。
- **FR-019**: 本能力的验证 MUST 至少覆盖：包序与目标集合（含 45/46 补丁）、阶段并发与间隔、重试次数与退避、失败即中止、失败不落库、两条入口的失败不回滚、Simulation/Hardware 装配。
- **FR-020**: 变更本能力时 MUST 同步更新本规范与 `docs/使用文档.md` 中「大屏模式」一节；无法在开发机验证的部分（物理画面）MUST 明确标注为未实机验证。

### Key Entities

- **视频墙布局模式**：`fullscreen-ws21` / `split-ws21-ws22` 两种物理布局，由运行态 `single/double` 决定。
- **下发序列与发送项**：阶段（清屏/映射/提交/刷新）、目标 `IP:端口`、原始包字节。
- **下发参数**：重试次数与退避、清屏到映射间隔、并发上限、单次超时；现场与开发环境共用一套默认值。
- **物理墙拓扑**：10×5 节点坐标、screen_id 到 IP 的映射及 45/46 互换补丁。
- **源与组播约定**：工作站 2-1 / 2-2 对应的组播地址、源分辨率与分块裁切参数。
- **切换结果**：成功（运行态与静音策略更新）/ 失败（保持原状 + 可定位错误摘要）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 自动化测试中，`single` 与 `double` 各自的包序、阶段归属与目标集合 100% 匹配（每次切换 200 个包：4 阶段 × 50 节点），补丁后的 IP 集合无遗漏、无重复。
- **SC-002**: 自动化测试可观测到「清屏全部完成 → 200 ms → 映射」的间隔，且同阶段并发 ≤25、阶段间不重叠；参数与旧版常量逐项一致。
- **SC-003**: 单节点在整段重试内不可达时，该节点的发送尝试次数恰为 5，退避为 0.2/0.4/0.8/1.0 秒；失败后其余阶段的发送次数为 0。
- **SC-004**: 下发失败时，运行态模式、静音窗口集合、预案的音量与窗口目标与切换前逐字段一致；接口错误码为 `video_wall_error`（运行态）或 `scenario_error`（预案）。
- **SC-005**: 墙面正常时 95% 的模式切换在 3 秒内返回；最坏重试场景在 90 秒内返回明确失败，静默超时为 0；等待期间其它控制台写操作不被阻塞。
- **SC-006**: Simulation 模式下切换产生的外发 TCP 连接数为 0，且非法模式仍被拒绝；Hardware 装配在测试中可解析出 TCP 实现与下发参数。
- **SC-007**: 现场（或等效带真实墙面的环境）按验证清单确认：单屏整墙无撕裂、双屏左右分区正确、RGB 测试卡边界与灰阶完整。取得现场证据前，本项 MUST 标注为「未实机验证」，不得计为通过。

## Assumptions

- **非目标**：拼接屏电源开关、跨屏拼接/帧同步、墙面节点健康监测与状态回读、像素级自动校验、把模式切换做成硬件原子操作（数据库事务不覆盖硬件副作用，只保证「失败即整体不生效」）。
- **验证边界**：开发机没有 50 节点墙面，物理画面只能现场确认。`docs/实机测试结论.md`（2026-07-26）中「单屏/双屏切换」「RGB 大屏画面」的结论属于**旧 Python 实现**，不能直接作为 .NET 版本的现场证据；.NET 版本在取得现场证据前按 SC-007 标注。
- **触发范围**：只有 `PATCH /api/runtime/` 与预案激活两条入口下发。控制主机重启、Supervisor 拉起播放器、显示器拓扑恢复都**不**自动重下发（保持旧版语义），墙面维持上次映射；需要重下时由操作员重复请求同一模式。
- **失败可见性**：失败以同步错误返回控制台；没有后台重试或补偿队列。运维人员可在排除网络故障后手动重试。
- **开放问题（待 `clarify`）**：控制主机重启或墙面掉电后是否需要自动重下发（当前答案：不需要，靠人工重复请求）。注意 `POST /api/system/restart/` 已经有同类先例——重启后由 `RuntimeStateService.ReapplyDisplayTargetsAsync`（`RuntimeStateService.cs:104`）按已保存目标自动恢复显示器落位，视频墙没有对应的重下发动作。若现场认为需要，应作为独立特性评审，不并入本次修复。
- 节点清单与端口的现场维护（新增/更换节点、IP 调整）不属于本轮范围；当前节点集合与 45/46 补丁按现场接线固化在实现中。
