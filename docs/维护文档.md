# SCP-cv 维护文档

## 1. 维护边界

当前生产代码由 `runtime-dotnet/` 与 `frontend/` 构成。旧 Django/PySide 运行时已删除，历史仅通过 Git 保留。旧 `db.sqlite3`、`media/`、`logs/` 和本地凭据属于用户数据，不随代码清理自动删除。

## 2. 目录职责

| 目录 | 职责 |
| --- | --- |
| `runtime-dotnet/src/ScpCv.ControlHost/` | REST/SSE、认证、健康检查、运行时协调 |
| `runtime-dotnet/src/ScpCv.Domain/` | 领域值对象与业务规则 |
| `runtime-dotnet/src/ScpCv.Infrastructure/` | EF Core、命令队列、媒体、设备、视频墙 |
| `runtime-dotnet/src/ScpCv.Supervisor/` | 运行组与子进程生命周期 |
| `runtime-dotnet/src/ScpCv.PlayerWorker/` | 两块大屏 WPF 播放器（窗口 1/2） |
| `runtime-dotnet/src/ScpCv.AudioWorker/` | 背景音频 |
| `runtime-dotnet/src/ScpCv.PowerPointHost/` | 唯一 STA/COM PowerPoint 宿主 |
| `runtime-dotnet/tests/` | Domain、Contracts、Infrastructure、ControlHost、Integration、Windows 测试 |
| `frontend/` | Web/Electron/Android 共享 Vue 控制台 |
| `docs/openapi.yaml`、`docs/paths/`、`docs/components/` | REST 合同 |
| `specs/` | Spec Kit 规范、计划、任务与验证记录 |

## 3. 依赖与镜像

.NET SDK 由仓库根目录及 `runtime-dotnet/global.json` 固定为 10.0.400，NuGet 包版本在 `Directory.Packages.props`，项目级 `packages.lock.json` 由 locked restore 校验。

Node 依赖只使用 pnpm，不使用 npm。仓库 `.npmrc` 指向教育网联合镜像站 `https://mirrors.cernet.edu.cn/npm/`；pnpm 锁文件不提交，前端 `package.json` 使用精确版本。安装命令：

```powershell
pnpm install
pnpm --prefix frontend install
```

Python 不再属于运行时。`.specify/scripts/python/` 和 `frontend/scripts/*_qa.py` 只是规范/QA 辅助工具，可由系统 Python 3 执行，不恢复 Django/pytest/uv 工程。

## 4. 配置与敏感信息

- `runtime-dotnet/src/ScpCv.ControlHost/appsettings.json`：默认非敏感配置。
- 命令行或标准 ASP.NET Core 环境变量：部署覆盖项。
- `frontend/.env`：本地 Vite 连接地址，不提交。
- 开发账号口令：使用 ACL 受保护的文件或 `SCP_CV_DEVELOPMENT_PASSWORD`。

不要提交密码、证书私钥、数据库、上传媒体、日志、打包产物或本地进程状态。`AllowedHosts` 与 `AllowedOrigins` 必须列出精确值，不要为排障改成无界通配。

## 5. 数据与备份

新运行数据默认位于 `data/dotnet/`，数据库为 `control.db`。ControlHost 是唯一数据库写入者，命令执行端不得直写数据库。

备份前应停止运行组，并同时保存：

- 当前 DataRoot；
- 媒体文件与派生制品；
- 部署配置和证书；
- 对应 Git 提交与 .NET/Node/pnpm 版本。

Git 只能恢复跟踪的代码和规范，不能恢复数据库、媒体、日志或 Office 状态。发现不兼容数据库时换用新的 DataRoot，不自动清空旧目录。

## 6. 验证基线

```powershell
dotnet restore runtime-dotnet/ScpCv.sln --locked-mode
dotnet build runtime-dotnet/ScpCv.sln -c Release --no-restore
$env:http_proxy=''; $env:https_proxy=''; $env:all_proxy=''
dotnet test runtime-dotnet/ScpCv.sln -c Release --no-build --filter "Category!=Physical"

pnpm --prefix frontend test
pnpm --prefix frontend run typecheck
pnpm --prefix frontend run build:web

py -3 .specify/scripts/python/validate_specs.py --specs-dir specs
pnpm --package=@redocly/cli dlx redocly lint docs/openapi.yaml
git diff --check
```

自定义 Host Header 的回环测试会受本机 `http_proxy`/`all_proxy` 干扰，因此常规测试先清空代理变量。改动源码后必须先构建再使用 `--no-build` 测试，避免执行旧二进制。

物理门禁单独报告：性能 1000/100 样本、两块大屏/Office/VLC/MediaMTX/音频长稳测试，以及视频墙和设备电源现场证据。D4 当前实测与停机恢复状态以 `specs/006-d4-live-convergence/verification.md` 为准，本机验证不可替代实机报告。

## 7. 运行与日志

启动和停止入口：

```powershell
powershell -File runtime-dotnet/scripts/run-headless.ps1 -SafetyMode Hardware -StartWorkers <其它参数>
powershell -File runtime-dotnet/scripts/run-headless.ps1 -Stop -DataRoot data/dotnet
```

状态查询使用已认证的 `GET /api/runtime/`；运行组启动/重启使用
`POST /api/system/restart/`，停机先执行 `POST /api/system/shutdown/`，写操作携带 CSRF。
确认自有 Worker/Office 退出后才停止同一 DataRoot 的控制面。`runtime.ps1` 的所有旧动作
已退役并返回明确失败；不得绕过 ControlHost 的代次、身份登记与两窗就绪门禁。

`run-headless.ps1` 将 ControlHost stdout/stderr 写入 DataRoot。各进程应保留独立日志，使用 command ID、target sequence、group epoch、generation 和 Worker 身份串联问题。

## 8. 故障定位

### 8.1 前端无法连接

检查监听地址、证书、`AllowedHosts`、`AllowedOrigins`、CSRF、Cookie 和防火墙。控制链路在线与 Worker 在线是两种状态，不要混淆。

### 8.2 运行组未就绪

检查 Supervisor 登记、PlayerWorker 1/2、AudioWorker、PowerPointHost 的 `WorkerReady` 与 heartbeat。缺少关键角色时 ControlHost 必须 fail closed，不得 armed；历史窗口 3/4 命令只保留审计，不再重放。

已认证 Supervisor 的原生进程退出会由 ControlHost 持有的 PID／启动时间／会话句柄观察确认，
当前运行组随后标记 `Faulted`，两窗显示错误／离线并保留原源和命令证据。临时断管不等于死亡，
旧组迟到退出也不能改写新组；首次数据库写入失败时日志事件 2215 保留死亡证据并退避重试。
`Faulted` 不等于整组已退出：先检查残余精确进程及自有 Office，再显式重启或协作停机，
取得退出证明后才终结旧执行租约。不要删除状态文件或直接改库来伪造恢复。

### 8.3 PPT 异常

默认 PPT/PPTX 上传经 PowerPointHost STA 导出 PNG，保存原件和逐页制品；播放器使用 `slide_images`，不创建 Office 放映窗口。检查准备作业的 queued/running/ready/failed/uncertain、摘要和缓存目录；missing 是页图未准备，不是原件丢失判定。普通两窗播放不能成为全局转换等待条件，只有原生 PowerPoint 放映占槽才暂缓。missing/failed 可显式 prepare，queued/running 可幂等复用，已有有效制品可直接 ready，不能从受理回执推断新建作业。uncertain 禁止直接重试，应先核查 Office；编辑抽屉已按源与打开周期隔离旧响应，取消后新抽屉不受旧准备结果影响。实验性原生放映默认关闭，仅影响后续打开；无法证明 PID/start-time/HWND 归属时不得强杀用户 Office。

状态排查要同时看页图实体截图、`current_slide` 和 `playback_mode=slide_images`；若画面/页码正确但模式为空，优先检查 Worker `state_report` 到 `RuntimeProjectionPublisher` 的字符串映射，而不是误判转换失败。

### 8.4 SRT/RTSP 异常

直播源由 `POST /api/sources/streams/` 登记为 RTSP、SRT 或自定义媒体流，`metadata.stream_status=unverified` 只表示尚未实际播出，不是在线结论；修改地址后下次打开生效。检查 MediaMTX（若使用它推拉流）、端口、流路径、VLC runtime 和缓存/latency 单位，并用独立解码及实体截图复核损坏帧。尤其核对 `tools/third_party/mediamtx/mediamtx.yml` 的 `writeQueueSize: 512`：D4 对照实测设为 8 时 RTSP 丢 H.264 包，API 仍可显示 `playing`。直播预热健康不等于物理画面已验证。

切换短视频时若 PlayerWorker 句柄逐轮增加，用 `runtime-dotnet/scripts/test-vlc-resource-stability.ps1` 对交互会话重复打开/关闭，比较预热后与停播 15 秒后的句柄；脚本要求明确 `DataRoot`、短视频源 ID、私有口令文件及现场备注，不操作窗口 3/4 或设备电源。LibVLC 实例应在一个 PlayerWorker 生命周期内复用，MediaPlayer、Media 与 WPF VideoView 则随源释放。

当前 .NET 播放器使用既有 NuGet 产物中的 `libvlc/win-x64`，不使用旧 Python／系统 VLC
自动兜底。SRT 告警应记录实际消费者版本与控制包形态：现有 VLC 握手为 SRT 1.5.3，辅助
FFmpeg 9.0.2 为 1.5.7，对 MediaMTX 零载荷 ACKACK 的校验结果不同。不能因独立解码零
H.264 错误就隐藏控制告警，有限回环也不能替代 D4 长稳；详见
[SRT 互操作证据与边界](qa/006-srt-interop.md)。

两窗基准入口 `benchmark-commands.ps1` 默认普通命令；健康热切换必须显式传入
`-Mode HotSwitch -SourceIds <至少两个健康源> -RawSamplesPath <CSV>`。
普通模式按本轮精确命令 ID 统计，所有命令须真实完成；失败、状态不明、折叠与未排空均不能
用低延迟掩盖。热切换另核实际源、代次、完成摘要和 Worker 身份，首错停止继续发令。
两种延迟分别是创建至开始、创建至控制完成，不是首个稳定画面的视觉延迟；测试后应恢复媒体状态。

### 8.5 视频墙模式无变化

大屏模式链路是 `VideoWallLayoutService`（另有预案兼容入口）→ `IVideoWallController` → 50 节点 4830。只有两个既有固定预设具有已知帧；笔记本、自定义 IP 与其它手动布局可持久化并预览，但在抓包前应用返回 `protocol_unavailable` 且不发送任何映射包。查看每个节点、阶段、尝试次数、退避和取消日志。`splice_screen` 的 8889 电源控制与 4830 画面映射不同。

### 8.7 媒体实体目录

新上传原件位于 `DataRoot/media/<页面文件夹>/<原文件名>`，临时上传文件先写入 `media/.staging/`；同名自动加序号，不覆盖旧文件。文件夹重命名/移动会同步更新子树受管理原件路径，正在播放/转换时拒绝；默认删除先搬出原件，含未登记文件时拒绝。`delete_contents=true` 才移入隔离目录并删除对应记录，数据库失败会补偿恢复。旧 `media/uploads/` 或日期目录只在用户显式移动对应源时转入新结构，不能批量自动删除。PPT 页图制品按源 ID/摘要独立存于 `DataRoot/cache/artifacts/`，移动原件时引用不变，备份时必须连同缓存一起保存。

单源删除也先隔离再提交，`media/.staging/deleted-source-<源ID>-<唯一ID>.json` 保存原路径及隔离路径。占用/只读原件返回 400 并保留记录；503 `media_cleanup_pending` 不能简单重试为成功。先以新数据库连接确认源记录是否仍存在，再决定恢复原件或清理隔离文件；查询失败、原路径已被其它文件占用或涉及重解析点时保留清单，不覆盖或猜测删除结果。

源移动遇到原件占用/权限异常时应返回 400 `media_error` 与“移动未生效”，原 URI 和下载内容保持。若遇到无内容 500，先核对代码版本和 `MoveSourceAsync` 的异常转换路径，不把文件系统异常当成前端离线或反复点击重试；已发生物理移动后的提交异常仍须按持久化路径确认后补偿。

### 8.8 视频画面与进度不一致

视频或直播的 `player_online`、HTTP 命令成功只能证明进程/命令链路，不能证明解码出帧。若实体截图持续变化而 `position_ms/duration_ms` 停滞，先检查 Worker 的 VLC 快照是否仅在控制命令完成时上报，再查空闲循环的周期 `state_report`、source generation 和 ControlHost 投影；不要通过重复发送控制命令掩盖进度缺口。长期内存与句柄趋势要与画面帧、同源重开和自然结束一起采样，见 006 验证记录。

### 8.6 系统音量与设备

检查 Hardware provider 是否识别交互桌面、默认渲染端点和显示器。硬件写失败不得把数据库意图伪报为已同步。预案路径与直接系统音量入口共用 `ISystemAudioController`，墙面→音量→原子状态提交→媒体命令的顺序及故障注入见 `docs/known-pitfalls.md` 坑 2。音量不可用返回 `system_audio_unavailable`；状态提交回执异常返回 `scenario_state_persistence_failed`，已经发生的硬件动作不自动补偿、不继续派媒体。先读回并核对，再恢复，不能凭一次失败响应假设硬件完全未变。

## 9. 发布与清理

发布前记录提交、SDK/运行时版本、验证命令、硬件条件和未执行项。不要使用 `git reset --hard` 或 `git clean` 处理未知改动。

清理数据库、媒体、日志、证书或本地运行目录前，必须停止相关进程并再次确认解析后的绝对路径。代码退役不授权删除这些用户数据。
