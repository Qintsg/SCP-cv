## 实际发现的稳定性问题

1. **视频自然结束后假“播放中”，循环未生效。** 120 秒 MP4 到 `01:59.967` 后停在同一帧。5 分钟、10 分钟的实体截图中 1 号屏像素完全一致，`loop_enabled=true`、API/前端仍为 `playing`，API 位置停在约 62.9 秒。`PlayerRuntimeHost.SetLoop` 在播放已开始后才向 Media 添加 `input-repeat` 选项，且没有 EndReached 重启路径。与 T136 的自然结束状态缺口相关，但还涉及循环语义。
2. **视频对同一源重复打开会黑屏。** 图片→视频正常；已播视频再次 `OPEN` 同一个源，命令表 `Completed/ok`、API `playing`，实体 1 号屏持续黑色；再次打开同源仍黑，切到图片再切回视频恢复。早期“暂停后黑屏”经隔离为同源重新打开导致；在正常出画状态下暂停/恢复均可用。需要核对 `PlayerRuntimeHost.OpenAsync` 的双 VideoView 置换和旧播放器释放次序，当前不推断单一根因。
3. **AudioWorker 暂停可能假成功且真实声音未停。** 重新播放 880 Hz 源后第一次 `PAUSE` 命令 `Completed/ok`，API 短时为 `paused` 后回到 `playing`；再次 `PAUSE` 才稳定保持 `paused`。在一次从 STOP 重新播放后的受控复测中，第二次暂停确认完成，录制前后 API 均为 `paused`，但六秒 WASAPI 回录的 880 Hz 幅度仍为 `0.000615`，与 playing 时 `0.000628` 接近；明确 `STOP` 后回录只剩 58 字节 WAV 头、无音频样本。`VlcAudioAdapter.PauseAsync` 直接调用具有切换语义的 `MediaPlayer.Pause()`，但仍需进一步定位异步状态/事件时序。
4. **视频重复打开后 Worker 私有内存显著增长。** 1 号 PlayerWorker 100 次混合切换后私有内存约 864 MB，而其它三个未高频切换的 Worker 为约 87–190 MB；关闭当前源 5 秒后仍约 783 MB。随后在 2 号 Worker 隔离复测：起点 104 MB；PNG/PDF 交替打开 40 次后 211 MB；PNG/网页 40 次后 213 MB；PNG/MP4 40 次后 749 MB；关闭当前源后仍 675 MB，数分钟后约 590 MB。三段每段 40/40 命令完成。`control-host.err.log` 同期出现多条 LibVLC D3D11 `SetThumbNailClip failed: 0x800706f4`。工作集回落较快，因此尚不能仅凭私有内存判定确定泄漏；但增长主要随 VLC 视频打开出现，应检查原生解码/渲染资源释放并跑更长斜率与 GPU 内存测试。
5. **PPT 首次页码上报为 0。** 文稿打开 8 秒后命令已完成，实体屏幕显示第一页，API 为 `current_slide=0,total_slides=9`；执行一次 `next` 后正确变成 2/9。需要补首帧页码同步，但动态放映和后续导航未因此失败。
6. **PDF 关闭后仍占用源文件。** 四窗均 `idle`、测试源已删除、计划任务已退出后，临时 `qa-stability.pdf` 仍返回访问被拒绝，等待后不释放；一次受控运行组重启后即可删除。`PdfPlaybackAdapter.DisposeAsync` 只将 `_document` 置空，没有显式释放 WinRT 文档对象；需查明并修复持有句柄的路径。
7. **运行组重启后状态文件丢失且旧 OfficeHost 遗留。** `/api/system/restart/` 在 7.4 秒内返回成功，新组 `Armed`、四窗 `idle/online`；但 `runtime-processes.json` 不存在，新 Supervisor PID 51936 下 7 个新受管进程在线，同时旧组 PowerPointHost PID 43664（13:19:11 创建、父进程已退出）仍存在。核对精确命令行与启动时间后，仅终止这个本项目旧宿主；没有按 `POWERPNT.EXE` 名称强杀 Office。代码中旧 Supervisor 的退出清理和新 Supervisor 都可能操作同一状态文件，需验证竞态并保证新组状态文件不被旧组删掉。**当前服务虽在线，下一次启停不应依赖缺失的状态文件直接继续操作。**

高码率 RTSP 探针曾出现大量 H.264 解码告警；同一流在本机 MediaMTX 回环也出现 `reader is too slow` 丢帧。降至 320×180/10fps 后首个 D4 本机探针零告警，但后续仍有少量告警；所以高码率结果不能直接归因于 D4 播放器，也不能把低码率流判为完全无解码错误。SRT 直读探针有 libSRT `INVALID SIZE` 告警，虽流路径持续 ready、入站错误帧为 0，仍不算 SRT 端到端画面验收。

首次切换压力脚本在截图任务仍写 PNG 时复制文件，部分检查点图像截断，**没有**计入实体画面证据；随后对四种源分别重新截图，并验证图像完整及画面内容。压力脚本的 100/100 是命令执行确认，不被这些截断图片提升为 100/100 实体逐帧验收。

## 验证边界与收尾

- 视频循环、同源重新打开、背景音频暂停均未通过，所以不能勾选 T116/T129 的 60 分钟混合稳定性门禁；T115 的普通写命令 1000 样本和网页健康热切换 100 样本也未由这次 GET/混合切换数据替代。
- 未做设备电源、视频墙实体映射、系统音量调节；未做人耳主观音质验收或独立声卡设备测量。
- 本次没有改动运行时代码。临时源 ID 13–18、列表、计划任务、推流进程、远端测试文件在收尾时清理；原有源 ID 1/2、原始媒体、数据库和凭据保留。受控重启后仍有 4×PlayerWorker、AudioWorker、PowerPointHost、MediaMTX 由新 Supervisor 管理，ControlHost 和网页保持在线，但状态文件缺失是未修复的高风险缺陷。
