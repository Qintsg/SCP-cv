# 输入路由与客户端直连预览（020）

2026-10-21已推送两个仓库并部署D4，运行包6c528ad、网页与代理92769c0，两播放器在线。配置保持、冷备、跨站预检与实体未验边界见[020部署记录](../specs/020-input-routing-preview/deployment.md)。本机测试包仍不是公开发行包。

## 页面操作

- 大屏选源采用已确认的方案A：窗口1／2／IP81／3／4为常用项，“其他输入”为可搜索、独立滚动的二级菜单。自定义仍填写设备IPv4，不是任意直播URL。
- 仪表盘不增加媒体库卡片。右侧依次为系统音量、电源、两台电视内容；电视各选一个输入，点击箭头应用。手动允许重发同样输入。
- 拼接屏电源按钮内的移动进度条只表示指令正在发送，无伪造百分比；关机仍需确认。两台电视仍使用原电源切换指令，不把切换当独立关机。
- 窗口3／4的预览分别为65／66，菜单页也可查看，但不能打开媒体或创建第三、第四个.NET播放器。
- 摄像机页只预览当前选中的一路；监控76可预览，不能转动。方向、变焦、机位确认和停止看门狗保持原行为。
- 预览只有1px边框：实际新帧绿色、丢失重连黄色、无法连接红色；没有预览流是中性空态。没有常驻大段说明或错误弹窗，悬浮和辅助技术可读取状态。

不存在75，也不生成D7-2。D4的窗口1–4与D4-1…D4-4是63–66的别名，不能当成八个独立输入。组播为登记的224.1.1.X:5000；并非任意IP都能自动推导并控制。

020部署时目录沿用工程统一4K声明，IP81为1080P；021已根据2026-10-21最新611A回读纠正为逐设备默认值并部署D4：18路4K、12路1080P，84未知。D4的63–66现已确认4K。管理员的`VideoWall:Inputs`受信描述可覆盖，但同IP的窗口/IP键冲突拒发。源尺寸、预览、电视输出和50节点目的尺寸是不同概念，不一起修改。见[输入尺寸维护](input-resolution-021.md)。

`/工作站`是内置、不可添加／编辑／移动／删除的目录。Hardware启动建立固定索引但不扫描网络；进入该目录或展开“其他输入”才请求有界端口发现。默认31项、最多6项并发、每端口250ms、TTL60秒，同一轮并发合并；仅连接554／1935，不拉媒体、不向客户端指定的任意地址探测。Simulation不连接网络，结果为unknown。

媒体列表只显示服务可达的工作站；离线记录仍保留ID供预案引用，不删源、不偷偷替换引用。TCP可达不保证媒体能解码。用户已有同名`/工作站`目录时不接管，返回冲突，需先自行改名。摄像机凭据仍使用既有服务端保存地址。

## 共享与首帧

Web继续沿用018的MediaMTX→服务器FFmpeg→HTTP-FLV／WS-FLV链路，观看电脑无需安装任何工具。020在同一应用内增加一个共享池：同一实际流只保留一条传输、一个视频解码器，再向多个canvas绘制；新消费者复用有效最近帧。

每个不同目标有一个不消费的验证租约，每个实际流另有一个消费租约；65个相同目标通常是2个租约，而不是65个上游。不同别名经服务端HMAC共享键合并，键绑定完整票据与实际规范URI，不对浏览器暴露凭据或裸URI哈希。最多64个别名参与共享续期，源修订改变时仅迁移受影响订阅。

几何、比例、布局码、标签及发送按钮忙态不改变流身份。清晰度是首次观看意图，不随矩形面积越过阈值反复切chn0／chn1；真正不同的协议、路径、通道、凭据不合并。最后可见引用约1秒宽限吸收组件重排；整页隐藏或认证／主机失效立即清需求，不把旧帧带到新账号。

关闭mpegts.js额外stash、受控服务器输出GOP缩到约0.5秒，仍保留完整GOP缓存、预算与慢消费者保护。5轮合成源对照冷首帧p50约4100→2915ms、p95约4150→3573ms；66个真实canvas仅一条流／一个解码器。这是本机合成链路结果，不是D4现场保证。

## Electron直拉

Windows x64客户端使用随包提供的自包含预览helper和FFmpeg，直接连接设备RTSP／RTMP，不经过D4的MediaMTX／FFmpeg；普通网页和Android不改为直拉。使用者无需另装Node、FFmpeg或.NET。

H264优先原码转封装、静音，不缩放原画面；不兼容时等待旧进程退出后，受控切为最高1080P／25fps、6Mbps的H264兼容模式。不能承诺任意编码无损，也不能消除源编码器自身的GOP等待。

渲染器只提交媒体ID或受限输入身份；敏感实际URI由主进程向当前已提交的主机固定API领取，沿用正常TLS、Cookie、CSRF、Origin，不跟随重定向。`app://scp-cv/__preview/…/stream.flv`仅有随机短能力，不包含地址／口令；不开放本地TCP端口、任意URL代理、进程参数或文件路径。沙箱、contextIsolation与webSecurity保持开启。

主机、完整登录票据、源修订、可信顶层窗口和租约共同围栏。最多6个本机流、128个租约含在途预留；helper通过私有stdin心跳存活，EOF／超时关闭自有KILL_ON_JOB_CLOSE Job，先挂Job再运行FFmpeg。进程异常或回收不确定时不能重起同键第二份。

**网络边界**：Web保留018的总出站限额与拥塞降档。Electron原码直拉绕开D4转码，但其入站码率由设备决定，不等同服务器8Mbps预算；本机进程资源限制也不是全机网络QoS。带宽不足可使用设备低清通道，或进入兼容编码；不能承诺任意网络下不断线，也不把整个ControlHost／MediaMTX降优先级。

## 电视协议与预案记账

电视左161／右162走各自4830矩阵端口：同一连接先6231满屏，再610D单源；不发送大屏的50节点清屏／映射／提交序列。6231+610D是项目明确组合，原矩阵构造与纯CPU黄金包、假Writer、本机TCP回环分别核验，不冒称现场电视出画。

服务端独立持久保存wall／tv_left／tv_right的上次完整发送意图、状态和时间。预案保存`advanced.televisions`，缺省保持；“从当前状态生成”只捕获完整成功发送记录。相同源参数与几何且记录可信时，预案跳过对应输出，不跳过其它音量、摄像机或媒体动作；仪表盘手动应用可强制重发。

发送前持久化dispatching；部分失败／取消／提交回执失败为不确定，不能沿旧成功记录去重。源IP相同但几何、裁切、协议配置不同仍要下发。电源操作使对应逻辑记录失效。记录不是设备实时读回，外部控制软件、掉电等可能使实体画面不同，必要时手动重发。

## 构建与发行

`pnpm --prefix frontend native:prepare --ffmpeg <固定exe> --sha256 <真实摘要> --license <许可证文件> --origin <HTTPS来源> --development-only true`仅准备本机验证资产。默认输出`.validation/client-preview-020/assets`，electron-builder的extraResources将其放入`resources/client-preview`，不查询全局PATH。

`pnpm --prefix frontend build:electron`先检查资产完整性与摘要，再构建本机目录包；默认不创建安装器、不发布。包装器使用已安装44.2运行时和当前锁定pnpm11.22，避免再次下载和误用全局11.24自动切版本；直接Node调用需显式`--pnpm-bin`，正常pnpm run从npm_execpath核对。目录包输出在`.validation/client-preview-020`独占子目录，不清空用户目录。公开分发须提供与二进制匹配的`--source-archive`、准确许可证／构建配置及第三方材料，并完成匹配审计；当前本机development-only资产不是公开发行包。FFmpeg含GPL组件时不能标为纯LGPL，“无商业属性”不免除对应义务。媒体二进制、源码包、测试CA、凭据与日志均不入Git。

自动化、真实合成媒体／Electron、本机只读截图与未执行现场项见[020验证](../specs/020-input-routing-preview/verification.md)。
