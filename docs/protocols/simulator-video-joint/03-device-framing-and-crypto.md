# 设备成帧、字节序与加密传输

相关资料：[业务帧](04-wall-matrix-audio.md)、[KVM 格式](06-kvm-and-auxiliary-services.md)、[验证](08-audit-and-verification.md)。

## 不同通道使用不同格式

| 标记 | 已定位的用途 | 注意点 |
| --- | --- | --- |
| `FB FC … FD FE` | 墙面、矩阵、音频和多种设备控制 | 同一帧头下也有型号或命令例外 |
| `FC FD … FE FF` | 多种设备应答与部分中控消息 | 不能仅凭 `FC FD` 就当作应答；KVM 也用这个开头 |
| `FA FA … FB FB` | IPC／控制服务相关消息 | 多个构造函数明确写零校验字段 |
| `FE FD … FC FD` | 字符串构造中的另一格式 | 变长 UTF-16 数据；没有相同的命令字段布局 |
| `F1 F2 … F3 F4` | 新传输模式的 DES 外层 | 内层仍是设备控制／应答消息 |
| `FC FD 06 01 … DE` | KVM 鼠标短报文 | 11 字节；无上述两字节累加校验 |

`FB FC` 家族中的 `2A 01` 等特殊报文还存在长度含义差异。不得把一个通用偏移表应用于命令全集。逐项入口见 `catalogs/binary-commands.csv`。

## 常见设备控制格式

对已验证的窗口映射等格式：

```text
head[2] command[2] controls[2] payload_length_be16[2]
payload[N] checksum_be16[2] tail[2]
```

多字节坐标、标识和端口使用大端。两个控制字节位于偏移 4、5，长度位于偏移 6、7。既有预设把控制字节设成零，因此历史 `00000021` 看起来像四字节长度；原函数实际分别赋值。

在完整 45 字节 `61 02` 映射帧中，校验和是 `sum(packet[2:40]) & 0xFFFF`。偏移 40 的模式字节不参与。历史实现的“把模式字节加入再减 1”只在该字节恰好为 1 时等价。

其它构造函数有不同校验范围，有些明确写 `00 00`。返回帧被原客户端接受，也不能证明校验字段正确：部分应答解析器只核对固定首尾和长度，不检查校验字段。

## 常见应答解析

`CTcpSocket` 的接收链路是：读取可用字节 → 加入环形缓冲 → 按型号／协议开关选择解析 → 发出窗口、音量、设备状态等信号。

旧模式缓冲容量为 `0x5000`，即 20480 字节。解析器通常返回：

| 返回值 | 处理含义 |
| --- | --- |
| `1` | 识别并消费一个完整消息，读指针前移 |
| `2` | 当前读位置不是该解析器接受的消息；上层可继续尝试其它类型／移动读指针 |
| `3` | 已有数据不足，保留读位置等后续字节 |

这不是 TCP 每次 read 对应一个消息的设计。半包、粘包、环绕和错误首尾必须单独处理。

已定位的解析器包括：`0x006634D0`、`0x00663C80`、`0x00664440`、`0x00664B30` 的窗口相关返回；`0x00668530`、`0x00668C50`、`0x00669370` 的其它窗口结构；`0x0066C530` 的音量返回；`0x0066D110` 的设备查询返回。字段全集仍按型号区分，未把这些地址都解释成同一应答布局。

例如 `FC FD 61 91 00 00 00 01 V … FE FF` 的解析器从偏移 8 提取一个字节，消费 13 字节，并核对固定首尾；它没有逐字节累加检查偏移 9、10。

## 新传输模式

`IsUseNewProtocol` 在设备发送 `0x007031E0` 与接收 `0x00708EB0` 的分支中生效。新模式使用：

```text
F1 F2 cipher_length_be16 ciphertext[cipher_length] F3 F4
```

明文是原控制帧。原程序：

1. 使用本地硬编码的八字节密钥生成 DES 子密钥。
2. 按八字节分组独立加密，即 DES-ECB。
3. 不足一组的明文尾部补零。
4. 传输长度取 `ceil(plaintext_length / 8) * 8`。
5. 外层长度是密文长度，不是内层 payload 长度。

这里不是 PKCS#7，也没有观察到随机 IV。密钥值保留在本地原代码证据，版本管理目录不提交它。调用者应显式提供密钥；不能拿 OpenAPI 登录密码作为 DES 密钥。

原始算法入口：`0x00690E50` 生成子密钥，`0x00691AA0` 处理分组，`0x006927B0` 处理待发送缓冲，`0x00692780` 返回输出缓冲地址。

隔离执行原算法与独立 DES 实现的五组明文完全一致，包括 12 字节清屏包、45 字节映射包、8／16 字节整组以及 23 字节非整组。详见 `samples/verification-summary.json`。

原多块辅助函数内部可能多计算一个零分组，但发送函数只复制上面的密文长度，因此整组明文不会额外传一个填充分组。

## 接收器的长度限制

原 `0x0066CFB0` 解析器不是完整的任意 16 位长度解析：它核对头部前 3 字节为 `F1 F2 00`，只从第 4 字节取长度。隔离测试确认，长度高字节非零时返回 `2`。

因此这条原客户端接收路径只接受小于 256 字节的外层负载；DES 分组负载的最大八字节倍数是 248。不能因为发送器写了两字节长度，就声称接收器支持 65535 字节。

八组原解析器测试覆盖完整包、仅头部、缺尾字节、跨缓冲末尾、错误头、错误尾、两包粘连和高长度字节。原测试结果保存为 `samples/stream-parser-verification.json`。

## 接入时的区别

协议下发、设备应答、实际画面是三个不同结果。现有 SCP-cv 传输成功表示控制包写出；原软件具备更多查询和应答解析，但仍没有证据证明每个控制操作都有逐包成功 ACK。

后续回读应先确定节点型号、请求／应答对和解析边界，再定义超时与状态投影。不能把任意 `FC FD` 包、一次 TCP 连接或客户端本地状态当作操作已完成。
