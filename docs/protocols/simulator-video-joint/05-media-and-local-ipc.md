# 媒体传输与本地进程间通信

相关资料：[地址用途](01-topology-and-lifecycle.md)、[相机代理](02-http-and-websocket.md)、[KVM](06-kvm-and-auxiliary-services.md)。

## 播放辅助进程

| 程序 | 已确认的通道 |
| --- | --- |
| `PlayCoreGroup.exe` | 加入 UDP 组播组；媒体接收与共享内存图像 |
| `PlayCoreSignal.exe` | UDP 单播接收；媒体接收与共享内存图像 |
| `PlayCoreRtmp.exe` | FFmpeg URI 输入，含 RTSP 连接选项；也保留 UDP 接收实现 |
| `VideoPreview.exe` | FFmpeg 预览、共享内存、关键帧 HTTP 请求 |
| KVM DLL | 预览媒体接收，加上输入事件发送 |

不要只根据 `Rtmp` 文件名限制其输入；原程序实际使用 `avformat_open_input`，并设置过 `rtsp_transport`、`stimeout`、`buffer_size`、`analyzeduration` 等选项。

辅助进程参数中存在 `video://{ip}:{port}&&{标识}`，例如原测试常量为 `video://224.1.1.53:5002&&1`。`&&` 是原程序自己解析的分隔符，不是提交给 shell 执行的命令连接符；启动进程时应作为完整参数值传入。

客户端还构造 `rtsp://…/live/chn0`、`/live/chn2`、`/live/chn{n}`、`video://…`、`audio://…` 和组合视频／音频路径。真实输入 URI 应按目录和型号生成，不从设备 IP 猜路径。

## 原生 UDP 媒体握手

`PlayCoreGroup` 的 `0x00403FA0`、`PlayCoreSignal` 的 `0x00403DB0`，以及 RTMP／预览／KVM 库中的同类实现使用 ASCII 控制消息：

| 文本 | 行为 |
| --- | --- |
| `GETHEADER` | 请求解码所需头信息 |
| `GETKEYFRAME` | 请求关键帧／恢复解码 |

发送目标使用媒体对象保存的地址和端口。组播程序加入该媒体组，再接收数据；没有证明控制消息总是发到独立控制端口。

获取头信息的循环最多尝试约 999 次，每次有 5 毫秒 sleep 及 Qt 事件处理。视频路径还设置 30000 毫秒计时器请求关键帧。丢失序列、队列异常等分支也会重新请求关键帧。

## 视频数据不是“裸 H.264 UDP”

视频解析跳过 12 字节首部，并从偏移 2、3 按大端提取序列值。剩余内容会累积成解码单元。它具有 RTP 风格首部，但不能据此认定完整遵守标准 RTP/H.264 打包。

`PlayCoreGroup:0x004039C0` 的实际分类规则：

| 检查 | 分类返回 |
| --- | --- |
| payload 前四字节为 `00 00 00 01`，随后是 `67` | `1` |
| 同样的起始码，随后是 `68` | `68`，保持原代码值 |
| 同样的起始码，随后是 `65` | `2` |
| 有上述起始码但未命中，首部第 2 字节为 `E0` | `7` |
| 有上述起始码但未命中，第 2 字节不是 `E0` | `4` |
| 没有上述起始码，第 2 字节为 `E0` | `6` |
| 没有上述起始码，第 2 字节不是 `E0` | `5` |

这里的数值是客户端内部分类，不是线上 opcode，也不是 NAL 类型的原值。`E0` 的结束标记分支用于判断何时把累积的数据放入解码队列。七组输入已在原分类函数上隔离执行，均与表中分支一致；不涉及实际媒体解码。

客户端存在恢复关键帧与跳过无效累积片段的处理。序列回绕和丢包计算还应按原函数逐项移植，不能直接假设任意标准 RTP 收包器都能替代它。

## 音频分支

音频接收使用独立队列。原代码检查开头 `FF F1` 来选择 AAC 相关路径，否则进入另一音频路径；该函数没有像视频路径那样统一去掉 12 字节首部。

因此，不能把同一个视频分片去头器套给所有音频数据。采样率、声道数、不同音频路径的载荷细节仍需对应输入配置和解码初始化资料；本轮没有声卡播放或网络录制验证。

## 关键帧 HTTP 请求

`VideoPreview` 和 `PlayCoreRtmp` 都保留关键帧HTTP请求。进一步读取辅助程序后确认完整路径为：

```text
POST http://{host}:9999/api/confcontrol/{cmConfId}/reqrtspiframe?cmConfId={cmConfId}
Authorization: <客户端保存的完整头值>
Content-Type: application/json

{"epId":"<终端标识>"}
```

`PlayCoreRtmp:0x00404BE0` 明确拼接 `:9999/api/confcontrol/`，所以这个请求不能仅按 `jsftServerPort` 推导。路径和查询都带同一 `cmConfId`，JSON仅含 `epId`。

这不是标准RTSP方法；它是会议配套服务的辅助HTTP接口。请求路径、字段和头已静态恢复，成功／失败返回的完整服务端结构仍待实测。契约已补入 [OpenAPI](contracts/http-openapi.yaml)。

## 图像共享内存

`PlayCoreGroup:0x00401740`、`PlayCoreSignal:0x00401730`、`PlayCoreRtmp:0x00408570` 等创建固定大小 `0x5EEC00` 的 Qt 共享内存。

图像发布格式由写入代码明确给出：

| 偏移 | 类型 | 内容 |
| --- | --- | --- |
| 0 | 本机 `uint32` | 图像宽 |
| 4 | 本机 `uint32` | 图像高 |
| 8 | 本机 `uint32` | 图像字节数 |
| 12 | 字节数组 | `QImage::bits()` 的内容 |

目标程序为 Windows x86，因此这些本机整数字段是小端。它没有使用设备帧的大端整数布局。

写端对共享块加锁，写宽、高、byteCount，然后复制像素，解锁。无图像持续达到阈值时会把共享块清零。像素路径可见 `QImage` 格式枚举 `13`；完整的行步长仍应随 byteCount 和具体 Qt 库核对，不能仅用 `width*height*3` 代替所有情况下的实际长度。

固定共享块大小是 6220800 字节，其中还包含 12 字节头。接入时必须将图像数据的容量与整个块大小区分；本轮没有启动这些原进程来写用户共享内存。

## 辅助进程停止信号

RTMP 路径另创建 4 字节共享内存，键由图像共享键加下划线和进程标识组成。`PlayCoreRtmp:0x00405C30` 周期读取首个本机整数；值为 `1` 时停止相应计时器、关闭播放对象并退出进程。

这个停止标志与图像的宽、高、byteCount 不在同一个块里。共享键、数据块创建／附加、主客户端的读取侧还需按同一版本的启动参数匹配。

## 剩余验证边界

- 已恢复辅助消息、UDP 分类和共享内存布局；未抓取现场媒体数据做独立持续解码。
- 音频的其它分支、某些输入的 RTP 头字段、序列回绕和辅助 HTTP 参数仍有待确认项。
- 编码输入不能由一个普通文件／RTSP URL 自动替代为组播 `GroupIp`；设备映射和软件预览使用的是不同链路。
